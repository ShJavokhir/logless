# NetBird bonus: verified implementation and demo playbook

Research date: September 26, 2026. This is a research memo, not a deployment. No accounts, infrastructure, DNS, or firewall rules were changed. Commands below are proposed examples with placeholders. Public primary documentation and versioned upstream source were checked; no performance or end-to-end availability claim is based on a live deployment.

## What the event asks for

The supplied bonus brief makes this an optional addition to either main challenge. Its three demonstrations are: a public NetBird reverse-proxy URL with no inbound application ports on the workload VM; access authentication that corresponds to a real role; and a URL whose lifetime follows its task/session. The video should show firewall state followed by a successful browser visit, the auth prompt, and a task URL becoming unavailable. Keep a service available for judging and include intended demo credentials in the README. The supplied participant guide lists a separate best-use-of-NetBird prize of $500 in Vultr credits; it does not specify numeric bonus points per tier.

These are requirements extracted from the user-provided documents, not independent instructions to provision infrastructure or publish credentials. Only dedicated, limited demo credentials belong in the public README—never cloud API keys, NetBird management tokens, enrollment keys, real customer credentials, or the participant credit code.

## The recommended design

Use two Vultr VMs if self-hosting:

```text
Judge's ordinary browser
          |
          | public HTTPS :443, role-specific authentication
          v
Vultr VM A: NetBird management + Traefik + NetBird proxy
          |
          | encrypted NetBird/WireGuard path
          v
Vultr VM B: application/orchestrator + NetBird peer
  public ingress to application ports: denied
  app listener: NetBird address, or firewall-protected interface
          |
          +-- isolated task sandbox 1 -> task-specific review endpoint
          +-- isolated task sandbox 2 -> task-specific review endpoint
```

The proxy and application have different exposure requirements. The bonus's strong practical claim is **no public inbound application ports on the application VM**. The edge proxy serving an ordinary internet browser still needs an internet-facing listener. A single VM can technically host both, but its open proxy port makes the claim harder to communicate and couples failures. The two-VM arrangement makes the boundary easy to verify.

Maintain two classes of URL:

1. A stable, password/SSO-protected product entrance for judges, created as a regular service through the dashboard/API.
2. Temporary task review URLs generated by the application as real work starts and revoked when it ends. These are the third-tier evidence.

For Challenge 1, expose only the intended review surface—such as a rendered artifact or a constrained browser viewer. Keep the sandbox runtime API, Docker socket, arbitrary execution endpoints, host admin console, and inference credentials outside that surface. NetBird is a network access layer; it does not replace execution isolation, filesystem restrictions, or egress policy.

This topology and separation are recommendations, not extra event requirements.

## The 90-second claim needs careful wording

The event brief says URLs expire about 90 seconds after the client stops. The [CLI documentation](https://docs.netbird.io/manage/reverse-proxy/expose-from-cli) describes a keep-alive every 30 seconds, a 90-second TTL, and graceful removal when Ctrl+C/SIGTERM reaches the client. It also says sessions are held in memory and disappear immediately on management restart.

**The latest source differs from that last explanation.** In v0.79.0, ephemeral services have a database-backed `LastRenewedAt`; renewals update the database. The reaper checks every 30 seconds for services older than a 90-second TTL, processes batches of 100, and starts after a small randomized delay. This means the TTL is not a wall-clock deletion guarantee. In a healthy steady state, deletion can require the next sweep after expiry; retries, load, or outages can make it later. Do not promise an exact 90-second deadline or immediate deletion on management restart. Those statements must be measured on the deployed version. [Reaper source](https://github.com/netbirdio/netbird/blob/v0.79.0/management/internals/modules/reverseproxy/service/manager/expose_tracker.go), [service manager, persistence and renewal](https://github.com/netbirdio/netbird/blob/v0.79.0/management/internals/modules/reverseproxy/service/manager/manager.go)

The same version's source caps simultaneous ephemeral exposures at **10 per peer**. Keep demo concurrency well under that limit. Client renewal and cleanup behavior are implemented in the [client expose manager](https://github.com/netbirdio/netbird/blob/v0.79.0/client/internal/expose/manager.go).

For the one-minute video, use a normal task completion path that sends graceful termination to its exposure process, then reload its former URL. Separately record a crash-recovery test with timestamps if useful. Do not spend the video waiting on a timer. Verify both the public URL and the service list: merely stopping the backend can produce a 502 while leaving the proxy service provisioned, which is weaker lifecycle evidence.

Also distinguish **ephemeral peer cleanup** from **ephemeral URL cleanup**. Setup keys can enroll ephemeral peers removed after more than ten minutes offline. Expiring or revoking an enrollment key does not disconnect already-enrolled peers. It is not a URL revocation mechanism. [Setup-key guide](https://docs.netbird.io/manage/peers/register-machines-using-setup-keys)

## Bring-up sequence

### 1. Establish the edge and DNS early

The [Vultr marketplace guide](https://docs.netbird.io/selfhosted/marketplaces/vultr) specifies a shared-CPU VM with at least 2 GB RAM, a domain, and DNS access. The image includes Traefik, the NetBird proxy, CrowdSec, and a local admin-user store. Its stack lives at `/opt/netbird`. The documented DNS example is:

| Type | Host | Value |
|---|---|---|
| A | `netbird.example.com` | edge VM's public IPv4 |
| CNAME | `*.netbird.example.com` | `netbird.example.com` |

Use DNS-only records when the provider is Cloudflare. The marketplace installer waits for DNS; inspect the Vultr console if setup appears stalled. Follow the generated proxy-domain configuration: some other guides use `proxy.example.com`, so do not copy a DNS suffix from a different topology.

The general [self-host quickstart](https://docs.netbird.io/selfhosted/selfhosted-quickstart) calls for at least one CPU/2 GB RAM and publicly accessible TCP 80/443 plus UDP 3478 on the control-plane host. Choose its built-in Traefik option and enable the NetBird proxy. These are **VM A** requirements. They do not mean opening application ports on **VM B**. No installer was run for this research.

Traefik sits in front of the management stack; the NetBird proxy performs the application's public TLS termination. Preserve TLS passthrough for proxy service hostnames. The [migration guide](https://docs.netbird.io/selfhosted/migration/enable-reverse-proxy) is the reference for an existing installation, including proxy tokens, Compose labels, wildcard DNS, and external-IdP callback setup. Prefer the fresh supported marketplace/quickstart path unless an existing deployment is already working.

### 2. Enroll the app VM and restrict its mesh access

Create a one-off setup key with an appropriate peer group; use that key to enroll VM B against the self-hosted management endpoint. Inspect `netbird up --help` on the installed version for the management-URL option, and check connection state with `netbird status -d`. Keep enrollment material in a restricted secret file/environment and out of repository history. [CLI reference](https://docs.netbird.io/get-started/cli)

NetBird creates a broad default All-to-All policy on new accounts. Create explicit replacement policies before removing it. Merely adding narrow rules while leaving the broad rule active does not restrict other mesh traffic. Only the trusted publication component should have permission to expose services. Keep untrusted sandbox processes away from the local NetBird daemon socket and management tokens. [Access policies](https://docs.netbird.io/manage/access-control)

An admin must enable Peer Expose in Settings → Clients and permit the relevant peer group. This authorizes the peer to create ephemeral services; it is separate from the authentication placed in front of a published service. [CLI expose setup](https://docs.netbird.io/manage/reverse-proxy/expose-from-cli)

### 3. Prove the listener is reachable through the mesh

The [troubleshooting guide](https://docs.netbird.io/manage/reverse-proxy/troubleshooting) explicitly warns that a backend bound only to `127.0.0.1`/`::1` is unreachable through normal peer-target routing. Bind to the NetBird IP where possible, or a suitable interface protected by the external firewall. Check the listener with `ss -tlnp` and verify from another authorized peer. Use target type `Peer` when the app runs on the machine with NetBird installed; self-targeting through a subnet resource can fail.

For containers, choose a deliberate mapping from a host/overlay port to the intended review service. Do not assume `ports: ["3000:3000"]` plus UFW is safe: Docker's official Ubuntu installation guide warns published container ports can bypass UFW/firewalld rules. Use the Vultr firewall boundary and a verified bind/network arrangement. Test both IPv4 and IPv6 if enabled. [Docker firewall limitations](https://docs.docker.com/engine/install/ubuntu/)

NetBird peers normally initiate outbound connections; blocked UDP can force relaying over TCP 443. Outbound control/relay connectivity must remain possible even while inbound app traffic is denied. An unusually strict egress policy needs the documented control, signal, relay, and STUN endpoints. [Ports and firewalls](https://docs.netbird.io/about-netbird/ports-and-firewalls)

### 4. Create the stable judging entrance

In Reverse Proxy → Services, create an HTTP service targeting VM B's peer and app port. Add a password or SSO policy that represents a real review role. Wait for successful provisioning and test from a browser without the NetBird client. Preserve this service throughout judging.

Keep the app's own permissions meaningful: a reviewer should inspect outputs and run safe sample tasks, not administer infrastructure. A shared demo password represents a review role, not individual attribution. SSO is stronger when demonstrating separate named users and groups.

Authentication methods combine as alternatives, not factors: SSO plus PIN means either can grant access. Header auth is intended for programmatic callers and strips the matching credential before forwarding. Authenticated sessions are scoped per service and documented as lasting 24 hours. Use a fresh/private browser window to prove the prompt. [Authentication guide](https://docs.netbird.io/manage/reverse-proxy/authentication)

### 5. Attach exposure to the task supervisor

Illustrative commands, not executed:

```sh
# Dedicated review service already listening on an allowed peer interface.
# Use an actual demo-only password supplied by the supervisor.
netbird expose 8080 --with-name-prefix task-42 --with-password "$REVIEW_PASSWORD"

# Alternative when the configured IdP has the intended reviewer group:
netbird expose 8080 --with-name-prefix task-42 --with-user-groups reviewers
```

The CLI supports PIN, password, SSO groups, protocol, name prefix, and custom-domain options; no header-auth flag is present in v0.79.0. For header-protected services, use the dashboard or API. Parse the actual returned URL rather than synthesizing it. [Versioned CLI source](https://github.com/netbirdio/netbird/blob/v0.79.0/client/cmd/expose.go)

Recommended supervisor contract:

```text
create task -> start sandbox -> verify review listener
            -> start exposure -> store returned URL and PID
            -> verify authenticated request -> show URL to user

finish/cancel/timeout -> stop exposure gracefully
                     -> verify route removal -> destroy sandbox
                     -> store final artifact and revocation evidence

unexpected exposure exit -> mark URL unavailable; never report it healthy
supervisor restart -> reconcile known tasks/exposures before resuming
```

A backend port being recycled for another task before the old exposure disappears can publish the wrong workload. Keep ports/task IDs reserved until revocation is confirmed. Give each task its own output identity and constrain the maximum lifetime independently of NetBird's keep-alive. These are application design precautions.

Source review also found a custom-domain nuance: v0.79.0's `ExposeServiceRequest.ToService` constructs `serviceName + "." + requestedDomain`, whereas prose CLI examples can read as an exact-domain mapping. Avoid depending on exact CLI custom-domain naming until tested; use its returned URL, or configure the stable name explicitly through the service API/dashboard. [Request-to-service implementation](https://github.com/netbirdio/netbird/blob/v0.79.0/management/internals/modules/reverseproxy/service/service.go#L1550)

## Automation/API map

Use a server-side service identity/token for infrastructure automation. Management credentials never belong in the browser or sandbox. NetBird API requests accept `Authorization: Token <PAT>`; OIDC Bearer authentication is also documented. [API authentication](https://docs.netbird.io/api), [service users and PATs](https://docs.netbird.io/manage/public-api)

| Purpose | Endpoint or reference |
|---|---|
| List/create regular reverse-proxy services | `GET` / `POST /api/reverse-proxies/services` |
| Read/update/delete service | `GET` / `PUT` / `DELETE /api/reverse-proxies/services/{serviceId}` |
| Discover proxy domains/capabilities | `GET /api/reverse-proxies/clusters` |
| Configure peer exposure permission | Account settings: `peer_expose_enabled`, `peer_expose_groups` |
| Enumerate app peer identity | Peers API |
| Request access evidence | `GET /api/events/proxy` |
| Read schema matching selected release | [v0.79.0 OpenAPI specification](https://github.com/netbirdio/netbird/blob/v0.79.0/shared/management/http/api/openapi.yml) |

Regular API services are an option for task URLs too, but our orchestrator must delete them and implement its own expiry/reconciliation; do not assume a POST automatically gains CLI keep-alive semantics. Store `serviceId`, task ID, public domain, intended role, creation time, desired expiry, and observed deletion result. The API provides target type/ID, port/protocol, enabled state, auth, redirect/host handling, and access restrictions. [Services API](https://docs.netbird.io/api/resources/services)

For Go projects, upstream has an embedded exposure API whose session object exposes `Domain`, `ServiceName`, `ServiceURL`, and `Wait(ctx)`. That can avoid parsing CLI output but adds integration work; CLI supervision is the smaller hackathon dependency. [Embedded expose API](https://github.com/netbirdio/netbird/blob/v0.79.0/client/embed/expose.go)

## Evidence and demo script

Recommended 15–25 seconds within the larger one-minute project video:

1. Show the **application VM** and its attached Vultr firewall rules; identify its IP and blocked application port.
2. Show an attempted direct connection failing from outside the mesh, then the NetBird public hostname reaching the auth gate.
3. Authenticate as the review role and open the task's actual result.
4. Finish/cancel that task in the product. Show its URL failing on a new request and its service removed, while the stable product entrance still works.

Use timestamps/task IDs across these views. Show the final real artifact, not only logs or a dashboard. A screenshot of firewall rules alone does not prove which VM those rules protect, and a cached browser page alone does not prove current connectivity. Use a new request/cache-busting parameter when checking revocation.

Record these supporting artifacts in the repository's demo notes:

| Claim | Useful evidence |
|---|---|
| Closed public app ports | VM identifier, firewall-group association, rules, failed external request |
| Traffic follows NetBird | Public hostname, proxy service target, successful request, proxy access log |
| Real role gate | Auth prompt, accepted reviewer role, rejected unauthorized attempt |
| Lifecycle binding | Task/exposure creation, graceful cleanup log, missing service, failed URL |
| Crash fallback | Last renewal time, forced client failure, measured disappearance time |
| Judge availability | Stable URL, dedicated limited credentials, cold-browser verification |

Proxy logs are available in the dashboard and through `GET /api/events/proxy`. Successful HTTP requests, authentication failures, and upstream failures have different status patterns. For restriction diagnostics, current documentation places the specific denial code in `auth_method_used`; `reason` can be generic. Avoid dumping IPs, cookies, tokens, or sensitive user data into the public demo artifact. [Access logs](https://docs.netbird.io/manage/reverse-proxy/access-logs)

## Likely failures and quick diagnosis

| Symptom | First checks |
|---|---|
| `PermissionDenied` from expose | Peer Expose enabled, allowed peer group, peer registered in correct account |
| URL exists but 502 | Backend port/listener; peer online; target is Peer; overlay firewall; container mapping |
| Certificate remains pending | DNS suffix and wildcard; edge 443 reachability; ACME challenge; TLS passthrough |
| App redirects to internal hostname | Public base URL, host forwarding, redirect rewriting |
| Authentication seems absent | Existing session cookie; fresh browser; service auth configuration |
| SSO works for wrong role | Group restriction, actual IdP mapping, alternative PIN/password bypass |
| Task ends but URL remains | Supervisor did not stop expose, cleanup request failed, or TTL sweep still pending |
| URL works after port reassignment | Old exposure not revoked before reuse; fix lifecycle ordering |
| Expose reaches limit | Ten-session-per-peer ceiling; clean up; constrain demo concurrency |
| Judges cannot load “private” service | NetBird-only mode selected instead of public HTTP with authentication |

For proxy-aware frameworks, configure the public URL and trusted proxy source deliberately. Backend traffic may arrive from a NetBird CGNAT address or, in Docker arrangements, a container bridge address. Trust the actual required scope; do not blindly trust all forwarding headers from arbitrary sources. [Backend service configuration](https://docs.netbird.io/manage/reverse-proxy/service-configuration)

Before submission, test the stable URL from a second device/browser that has no mesh membership, verify the credentials, and leave the cloud VMs/process supervisors running. Do not attach the judging URL to a laptop terminal that closes overnight. If it must be ephemeral, supervise it and update any published URL after a restart; a regular stable entrance avoids that churn. Keep a second task ready for lifecycle demonstrations and avoid upgrading NetBird during judging.
